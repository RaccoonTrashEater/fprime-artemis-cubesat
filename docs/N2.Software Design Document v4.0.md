1. Introduction
1.1. Purpose
This document is the software design for the Neutron-2 flight software. It states what the
software does, which component owns each responsibility, how the design meets the flight
software requirements, and what evidence is required before each hardware stage. It is written
for students joining the software team.

1.2. Scope
In scope: onboard command and telemetry handling, mission modes, payload sequencing,
science storage and downlink, subsystem coordination, fault detection and recovery, command
authentication, and the flight-to-ground interface. Out of scope: payload acquisition firmware,
vendor ADCS control algorithms, electrical protection circuits, RF performance, and ground

interface to them, completed through the ICD.

1.3. Overview
The flight software is C++ on the F Prime (F′) framework. Mission logic is shared between the
Artemis FlatSat engineering model and the flight build; only the hardware adapters change. The
flight computer is the ISIS iOBC running FreeRTOS, the only operating system the vendor
documents for the board [S4]. F′ does not list the iOBC as a supported platform, so the port is
work for the team with three open items: the application code budget against 1 MB of NOR
flash, the operating-system abstraction port, and the scheduling model (Section 9.1, OD-01).
New students should read Section 3 for the architecture, Section 5 for the mission sequence, and
Section 12 for the contribution workflow before taking a task.

3. Software Architecture
The iOBC runs the team-owned C++/F′ deployment. The payload computer and the vendor
ADCS algorithms are outside that boundary. The Artemis Pi/Teensy arrangement is the FlatSat
transport. Figure 1 separates the team’s software from external devices and ground tools. [S5,
S6]

The context boundary shows responsibility, not electrical layout. Flight bus selections and
message formats are in the ICD.

3.1. Layers
Applications own mission sequences and policy. Managers expose typed, hardware-independent
subsystem operations and report achieved state, validity, and errors. Drivers adapt those contracts
to the selected hardware or simulator. Vendor SDK calls stay below the manager contract;
mission applications never call board, OS, or vendor APIs directly. Figure 2 shows the layers;
Table 4 lists the hardware substitutions. [S6, S8]

## PDF page 10

Each deployment is a separately built executable. Host simulation runs mission logic without
hardware. FlatSat runs on the Pi-hosted F′ with Artemis bridge hardware. Flight targets the iOBC
after its feasibility gate. Subtopologies group services, mission logic, managers, and platform
adapters inside one deployment; they are not separate processors.

3.2. Command authority and framework services
MissionApp is the only component that changes spacecraft mode. ScienceApp and
PayloadDownlinkApp request or execute authorized activities. Subsystem managers never
change mode. Hardware protection may act on its own and then report its state to the software.
Ground requests pass through the command service and the mode and interlock checks.
The design reuses F′ command dispatch, events, telemetry, parameters, rate groups, health
monitoring, and bounded buffer and file services. Component execution types, queue sizes, task
priorities, and the inclusion of sequencer and file-transfer services are chosen and measured per
deployment. Framework health monitoring does not replace the mission fault policy or the
hardware watchdog.

3.3. Why F′
F′ provides typed component interfaces, generated command and telemetry definitions, test
harnesses, and a working FlatSat starting point. Its costs are learning FPP and C++, managing
asynchronous execution, and building the iOBC port. If the iOBC feasibility milestone fails, the
team documents a platform trade and decides before changing the baseline. [S6, S8]

3.5. Component contracts
Operation names below describe intent. Typed ports, command IDs, queue sizes, and execution
types belong in the FPP model. The remaining managers follow the same pattern using Table 3
and Section 4.2.
MissionApp
Inputs: Ground commands, schedule triggers, subsystem health, activity results.
Outputs: Accepted or rejected requests, mode changes, authorized science or recovery actions.
State and failure: Owns mode, schedules, and recovery policy. Rejects failed guards. After reset,
establishes the inhibited startup state and revalidates persisted activity before use.
ScienceApp
Inputs: An authorized collection request, payload status, storage results.
Outputs: Payload acquisition, Standby, and transfer requests; product writes; completion or
failure reports.
State and failure: Owns the active sequence and attempt identity. On timeout or cancel, preserves
the partial attempt; a restart gets a new attempt ID.
PayloadManager
Inputs: Standby, configuration, start/abort, product-transfer requests; driver status.
Outputs: Adapter requests; achieved-state, progress, completion, or error reports.
State and failure: Owns payload operation state. A missing response is unknown state.
Reconciles with the device after reset before allowing acquisition.
StorageManager
Inputs: Capacity reservations, bounded product writes, finalization requests, delivery updates.
Outputs: Admission decisions, product handles and status, available capacity, integrity errors.

4.2. Common contracts
Every asynchronous request carries a correlation identifier and has an explicit completion or
failure result. Subsystem reports distinguish requested from achieved state and carry observation
time, source validity, and age; a stale reading is reported as stale, not as a value. Commands
validate arguments, mode permission, readiness, and inhibits before execution; acceptance and
completion are separately observable.
Product operations identify product and attempt, chunk size, offset, completion state, and
integrity result. Storage operations define buffer ownership and lifetime. Adapters serialize
transactions where required and enforce bounded timeouts and retries. A missing response is an
unknown state, never success. Final FPP types and limits are ICD and dictionary work.

4.3. Scheduling and resource isolation
Long payload, storage, and radio transactions run outside time-critical polling and health paths.
Bulk data moves in bounded chunks with backpressure; unavailable buffers delay or reject work
rather than allocating. Queue overflow, stale telemetry, storage exhaustion, and timeouts produce
observable results. Priorities and rates must keep command handling, health reporting, and fault
response alive during collection or downlink.
Bulk science shares the framer and the SDLS stage with telemetry and events. The isolation
available is queue depth, queue priority, and buffer binning, not path separation (Section 8.5).
Throughput under simultaneous science downlink and telemetry is a Section 10 gate
measurement. [S8]
Time-tagged and geolocation-tagged schedules persist with identifier, trigger, validity window,
duration, execution state, and restart policy. After reboot or recovery, triggers are revalidated
against valid time and location; a trigger with an invalid source is held. Persistence format and
trigger tolerance are TBD.

4.4. F′ execution
A component owns behavior; a typed port is its interface; a topology instantiates and connects
components. Passive components have no thread or queue. Active components have both.
Queued components have a queue that another context dispatches to. Synchronous calls run on
the caller’s thread; guarded calls also serialize; asynchronous calls queue at the receiver. These
are chosen deliberately, not by naming convention. [S8]
Rate-group callbacks stay short and bounded. Slow payload, file, and radio work runs in a
worker or an incremental state machine with explicit completion, timeout, and backpressure.
Buffers are returned on success, failure, cancellation, and reset. F′ Health pings prove software
responsiveness only. These patterns assume a pre-emptive OS, which the iOBC’s documented
FreeRTOS configuration is not; Section 9.1 carries that item, and until it closes, every long
synchronous call is treated as blocking the whole deployment. [S4, S8]

5. Operational Modes and Sequences
Table 5 defines the seven flight modes from MOP v2.0 §8. FSW-001 requires the software to
perform each permitted mode change defined there when its manual, queued, or automatic
trigger occurs, and its entry conditions are met. FSW-013 requires booting to a safe mode with
minimal subsystem activation after any reset or power cycle. The neutron_2 code implements
five demo states (BASE, COLLECTION_PENDING, COLLECTING, SCIENCE_READY,
DOWNLINKING); the seven-mode model is a planned extension. A transition completes only
after the required achieved states are confirmed. [S2, S5, S6]
A guard is a condition that must pass before a transition or operation is allowed; a failed guard
rejects and reports the transition. Figure 3 shows the principal transitions. Implementation tests
must cover every enabled transition and its guards.
MOP v2.0 §8 also requires commissioning flags. On every mode entry, MissionApp evaluates
the persisted flags and assigns each subsystem the operational state its commissioning status
allows; for example, ADCS in Base is Y-Thomson until the three-axis flag is set, then nadir
pointing. Flags change only by ground command and are recorded in the critical parameter store
(Table 6). A missing or invalid flag selects the least-capable state.

5.1. Nominal science sequence
Ground enables a valid activity. MissionApp checks mode, trigger, payload readiness, storage
admission, and active faults. ScienceApp commands collection through PayloadManager. When
acquisition ends, the payload returns to Standby and transfers the product to OBC storage.
StorageManager marks the product complete only after the interface completion and integrity
checks pass. A later contact transfers the product and its context; ground receipt is recorded
separately from transmission. Figure 4 shows the accepted path.

5.2. Interrupted collection and restart
After a ground-commanded Safe exit, MissionApp may restart an interrupted collection if its
science window is still valid and all admission checks pass. The prior attempt is kept as partial,
and the restart gets a new attempt identifier. Working assumption: enough time must remain to
complete the requested duration; otherwise the activity is skipped and logged. Systems
engineering and the payload and operations owners decide whether shortened collections are
allowed (OD-04).

6. Science Data and Ground Operations
6.1. Product and metadata model
The payload acquires internally and supplies CSV-like science products. The OBC transfers,
stores, tags, and downlinks them, and generates a reduced-volume version of selected science for
the UHF backup path (FSW-012). CSV encoding is a working assumption, not an approved
payload contract. Format, maximum product size, cadence, and retention are confirmed with
systems engineering and the payload team (OD-02). [S2, S5]
Two product classes exist. A raw product preserves the payload bytes unchanged. A
reduced-volume product is derived from one or more raw products by compression or
summarization; it is a separate catalog entry that names its source product and attempt, carries its
own integrity value, and never replaces its source. Ground confirmation of a reduced product
does not make the raw product deletion-eligible. The reduction algorithm, its CPU and memory
cost on the 400 MHz ARM9, and the integrity meaning of a derived product are OD-02.
Each product carries the spacecraft identifier, product and attempt identifiers, collection start and
end time, payload configuration, completion status, integrity information, and position, altitude,
attitude, and magnetic-field context with validity and source timing. FSW-005 requires time,
latitude, longitude, altitude, attitude, and magnetic-field direction and magnitude for the
measurement interval, so the magnetic-field fields are mandatory. Invalid context is flagged,
never replaced with a fabricated value. The data dictionary allocates per-record versus
per-product context.
Time. OBC-010 requires onboard time synchronized to UTC within ±0.5 s, and FSW-005
requires time to be recorded for the science measurement interval, so clock discipline is software
work. The iOBC RTC is the running clock. A valid GPS time fix corrects it; it logs each
correction and its age. Every timestamp carries its clock source and estimated error. After a reset,
the clock is unsynchronized until the next valid fix or a ground time update; records taken in that
state are flagged, not discarded, and ground correlates them from the logged corrections. Drift
measurement, the accuracy budget, and the ground time-update command are OD-08. [S2]

6.2. Storage and retention
The catalog distinguishes raw and reduced products and, for each, the partial, complete, selected,
transmitted, ground-confirmed, and deletion-eligible states. Receipt acknowledgment identifies
the product and integrity value so confirmation cannot land on the wrong attempt or class.
Missing or ambiguous confirmation leaves the product retained.
FSW-006 requires storing each state-of-health record received from a powered subsystem during
the previous 48 hours and making it available to COMMS for downlink. That window is the
floor on the engineering-log allocation and the fault-evidence budget Section 7 spends. System
Budgets v2.1 sizes it at about 978 kB; OBC-002 carries the hardware side. [S2, S14]

7. Fault Detection, Isolation, and Recovery (FDIR)
This section defines how a fault is detected, which tier may act on it, and how the spacecraft
recovers. FSW-level parents: FSW-007 (Safe entry on assigned indications), FSW-011 (rate
monitor and inhibit), FSW-013 (safe boot), FSW-006 (48-hour SOH evidence). System-level
parents: OBC-007, OBC-008, OBC-009, OPS-008, and OBC-005 (Section 7.3). FDIR is built on
the F′ services in Section 3.2, the manager contracts in Section 4.2, and the CCSDS stack in
Section 8; it does not depend on PUS services. [S2, S8, S11]

7.1. Safe entry and authority
Subsystem managers and framework health services report faults; MissionApp owns Safe entry
and exit. FSW-007 separates the software transition from the sensor thresholds and hardware
detection that produce the indication. The low-power threshold is allocated by OPS-011 (30 %
state of charge) and owned by EPS and operations; FSW consumes the EPS indication and does
not evaluate state of charge itself. Fault severity, persistence, thresholds, output states, and the
power-positive Safe configuration require EPS, ADCS, systems, and operations approval
(OD-03). Hardware protection is independent of software responsiveness. [S2]

7.2. Safe exit

FSW-001 binds the software to the MOP’s mode changes. When the command arrives,

input is within recovery limits and has stayed healthy for a configurable stability interval; no exit
path bypasses separation inhibits or subsystem protections; a latched or nonrecoverable fault
rejects the command until ground clears the latch. After a watchdog reset, the software first
establishes the inhibited startup state FSW-013 requires and reassesses health; it does not restore

8.1. Requirement basis

8.5. Three constraints
First, the crypto component must be passive with synchronous handlers. SdlsSaRouter
requirement SVC-CCSDS-SDLS-SA-ROUTER-008 requires downstream crypto components to
invoke the return ports synchronously on the caller’s thread; an asynchronous or
hardware-backed component cannot be connected without external synchronization. On a 400
MHz ARM9 without cryptographic acceleration, the cipher therefore runs on the framing thread.
Its cost is a Section 10 gate measurement, and under a cooperative scheduler a synchronous
cipher call blocks every other task (Section 9.1). [S4, S8]
Second, per-channel separation is by SA index. TmFramer supports exactly one virtual channel
per instance (SVC-Ccsds-TM-FRAMER-008); TcDeframer accepts all virtual channels or one
configured channel, so the constraint is on the downlink side. Multi-channel framing would need
multiple framer instances with no pre-built pattern. [S8]
Third, bulk science shares the framer and SDLS stage with telemetry and events. FileDownlink
feeds ComQueue’s FILE lane with its own depth and priority, and BufferManager has a separate
larger bin for file buffers, but everything downstream of ComQueue is shared. Science gets a
different SA index, not a different path. [S8]

8.6. Frame profile
AosFramer and AosDeframer do not support SDLS, the Insert Zone, or the Frame Header Error
Control Field. AOS is otherwise the more flexible choice for virtual channel management;
choosing it forfeits the SDLS processing stage. The FSW-009 frame profile and the protection
design are therefore one decision, OD-13, owned by COMMS with the FSW lead. COMM-008
permits AX.25, which would conflict with FSW-009 and SYS-009, and its
amateur-ground-station rationale predates the Part 5 plan; the COMMs requirement owner and
systems engineering resolve it (OD-13). [S2, S8]

8.7. Key handling and replay protection
Keys are pre-loaded symmetric keys with no in-flight rekey. Rekey is the largest single source of
lockout risk: an interrupted, misordered, or misapplied rekey leaves a spacecraft that cannot be
commanded. If a flight key is compromised, the response is operational: stop commanding until
the situation is understood.
Keys live in the critical parameter store (Section 7.3) with one cold spare in NOR. F′’s
SdlsFileKeyManager reads a key from a file per request and is not used; N2 substitutes its own
key manager behind the Svc.Ccsds.SdlsKeyInterface. [S8]




                                              Neutron-2.Software Design Document v4.0. Pg. 29

## PDF page 30

Replay protection is a monotonic counter in FRAM. A command is accepted only when its
counter exceeds the last accepted value within a forward window wide enough to tolerate uplinks
lost to a bad pass. The counter is persisted before the command executes; persisting afterward
leaves a reset window for replay. Window width is TBD (OD-13). Resynchronization: the
current accepted counter is downlinked in SOH; operations send the next command with counter
plus one. The counter is not secret.
There is no unauthenticated bypass and no recovery backdoor. Recovery from a damaged key
slot is via the redundant slots and the NOR cold spare. Failed verification is counted, evented,
and rate-limited; it never enters Safe and never latches out commanding, because otherwise
anyone able to transmit on the uplink frequency could take the spacecraft out of contact.
Key loading is an EGSE bench procedure with a verification step before the unit is closed out.
FlatSat and host deployments use ClearText components or test keys. Flight keys never enter the
repository. Export-control review of any cryptographic source in the repository is an OD-13 item
owned by the principal investigator.

8.8. Requirement trace and non-goals
UNP12-92 is the parent for uplink encryption. FSW-010 requires rejection of ground or internal

Appendix A. How Commands and Telemetry Move
Through F′
Section 8 refers to pieces of the F′ v4.3.0 communications stack by name. This appendix walks
through what those pieces do so the design can be read without the framework source open.
Everything here was checked against the pinned checkout [S8]. Component names appear once
each so a student can find them in the repository.
The path down: telemetry, events, and science to the radio
Every downlinked item starts as a buffer handed to a queue. The queue is the first place the
design gets any control: it has separate lanes for telemetry, events, and files, each with its own
depth and priority, so a large science file waiting to go out cannot starve a health packet. The file
lane draws from a separate, larger pool of buffers than the packet lanes, which keeps science
transfers from exhausting the small buffers telemetry needs.
From the queue, each buffer is wrapped in a CCSDS Space Packet. The packet framer stamps it
with an application process identifier, the APID, which tells the ground what kind of data it is,
and with a sequence count that increments per APID so gaps are detectable. A small
bookkeeping component keeps those counts. This is the layer FSW-009 cares about: after this
step, the data is a standard Space Packet and stays one all the way to the ground.
Packets are then gathered into a transfer frame. The TM framer builds the frame, tags it with a
virtual channel identifier, maintains its own frame counters, and appends a 16-bit cyclic
redundancy check so the ground rejects a corrupted frame rather than decoding it into garbage. In
this framework, the TM framer handles exactly one virtual channel per instance. That single fact
drives Section 8.3: because the design cannot cheaply give science and telemetry different virtual
channels, it separates them with the security association index instead.
Finally, the frame goes to a stub that hands bytes to whichever driver talks to the radio. The stub
exists so the same stack works over a UART on FlatSat and over the SPI link to the flight radio.
The path up: a command from the radio to its handler
Bytes arriving from the radio go to the same stub, then to an accumulator that watches the stream
for the start of a valid telecommand frame. The accumulator uses a detector tuned to the CCSDS
telecommand frame format; until it sees a well-formed header and length it discards noise. This
is the first defense against a bad pass: garbage never reaches the deframer.
The telecommand deframer strips the frame and checks it. Unlike the TM framer, it can accept
all virtual channels or be pinned to one, so on the uplink side the virtual channel could be used as


                                                Neutron-2.Software Design Document v4.0. Pg. 40

## PDF page 41

a filter if the packet profile calls for it. The Space Packet deframer then recovers the packet and
reads its APID, and a router sends the packet to the command dispatcher or, for uploads, to the
file uplink service. The command dispatcher looks up the opcode, validates arguments, and calls
the handler in the owning component. Mode permission, readiness, and inhibit checks (Section
4.2) happen in that handler, not in the stack.
Where protection sits
The SDLS processing stage uses a pair of components inserted between the Space Packet layer
and the transfer-frame layer, one for each direction. On the way down, after packets are built but
before the frame is sealed, a protection framer passes the data to a router that reads the security
association index from the frame context and picks the crypto instance registered for that index.
The crypto instance encrypts and authenticates, or only authenticates, according to that
association, and the result goes on to the TM framer. On the way up the order reverses: the
telecommand deframer hands the frame to a protection deframer, the router picks the instance for
the index carried in the frame, and only a frame that verifies reaches the packet deframer.
Because protection wraps the packet rather than altering it, the Space Packet the ground sees is
the same one FSW built, and FSW-009 still holds.
The framework ships this SDLS processing stage with a pass-through crypto component whose
own model file says it provides no confidentiality, integrity, or authentication. It is there so the
stack can be tested in the clear. The N2 work is one component that implements the same encrypt
and decrypt interfaces with a real cipher and MAC, plus a configuration file that names it instead
of the pass-through. No framework file is edited, which is why upgrades stay cheap.
The crypto component needs keys. The framework’s shipped key manager opens a file and reads
the key every time it is asked, which suits a Linux host and not a spacecraft with keys in FRAM.
N2 replaces it with a key manager that implements the same key interface but reads from the
critical parameter store of Section 7.3.
Two constraints that shape the design
The router calls the crypto component synchronously and expects it to answer on the same thread
before returning. The router’s own requirements document says so, and the reason is that the
router holds a lock while it waits; a crypto component that queued the work and answered later
would deadlock it. The consequence for N2 is that the cipher runs inside the framing thread on
the ARM9 with no hardware acceleration, so every frame pays the cipher cost in line. That is
why Section 10 requires the cost to be measured before the throughput budget is set, and why the
cooperative-scheduler question in Section 9.1 matters: on that scheduler the cipher would stall
every other task while it runs.
The alternative AOS frame format is more flexible for virtual channels, but the framework’s
AOS framer and deframer do not support the SDLS processing stage; their design notes list it as
disabled. Choosing AOS for FSW-009 would therefore remove command authentication. The
frame profile and the protection design are one decision, OD-13.
