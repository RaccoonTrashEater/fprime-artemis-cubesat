## What can be reused

The existing application/manager/driver pattern is the right seam. F′'s checked-out [layering guidance](../../ArtemisRpiTeensy_N2/lib/fprime/docs/user-manual/design-patterns/app-man-drv.md) describes replacement of lower layers for simulation and reuse. The [driver guide](../../ArtemisRpiTeensy_N2/lib/fprime/docs/how-to/develop-device-driver.md) distinguishes device operations from bus operations. Our payload facade can expose an Aris-owned private device implementation below the public manager contract without exposing private command encoding in mission applications. USB↔RS-422 was selected October 18; adapter/settings, public command/lifecycle and raw-file details still need confirmation.

`MissionApp` and `ScienceApp` already cover mission coordination and science sequencing. Extend those components unless an actual ownership problem requires another component. Keep scheduled FSR behavior under one mission authority; avoid creating a competing mode controller. The current topology already connects mission, science, payload, storage, communications, and downlink components ([topology](../../ArtemisRpiTeensy_N2/ArtemisRpiTeensyDeployment/Top/topology.fpp), lines 171–192).

For the local testbed, host-native F′ replaces the Pi executable, while simulated payload/EPS/radio interfaces replace unavailable boards. Preserve mission contracts, command names/IDs where practical, and data semantics; record topology/driver substitutions. This proves software behavior against simulated contracts, not Pi timing, the physical PLD interface, radio performance, or iOBC portability.

## Public contracts before private implementation

Use two levels so the temporary mechanism can evolve without rewriting mission logic:

1. **Initial opaque command facade:** a literal command string enters F′ from Yamcs and reaches a simulated Aris facade unchanged. The simulator returns a response correlated to that request. Use consistent FPP storage and framework framing, without adding a separate radio-derived string limit. Do not invent or issue real private opcodes.
2. **Mission collection contract:** `MissionApp/ScienceApp → PayloadManager` requests an operation with an identifier and receives only the accepted/rejected/progress/completed/failed/timed-out reports supported by the agreed payload API. A completed raw product descriptor is a separate result with attempt identity, bytes, integrity, and finalization state. The payload transport and file boundary are open; do not assume USB/RS-422.

Start with one operation in flight. For local slice C, `PayloadManager` is the sole admission point for literal pass-through, current capture, and legacy/scheduled capture requests. Carry a Yamcs-visible request ID plus an internal operation generation through dispatch and callbacks. A competing valid request using the active request ID is `BUSY`; zero synthetic request ID or explicit legacy collection ID, empty literal, and invalid duration are `INVALID`. Reuse after terminal completion creates a new generation. Emit `ACCEPTED` at most once after dispatch, then exactly one terminal outcome: `COMPLETED`, `BUSY`, `INVALID`, `DRIVER_UNAVAILABLE`, `FAILED`, or `TIMED_OUT`. Admission rejection may return its terminal status without `ACCEPTED`. Ignore duplicate, post-terminal, or generation-mismatched callbacks; a reused request ID must not let an old callback complete a new operation. Missing response is `TIMED_OUT`, never success (SDD p. 14). Duration-only commands allocate request IDs internally; `requestIn(0, duration)` requests allocation rather than supplying an explicit zero ID.

Only a successful capture with a validated product descriptor/data may be forwarded to `ScienceApp` or recorded by Storage. A successful literal pass-through returns its command result only and must not create capture/product evidence. A failure/timeout, malformed descriptor, stale callback, or duplicate callback must not increment collection completion, emit science-ready evidence, or create a product/storage record. The simulated capture child must have a configured deadline; timeout/hang must terminate and reap it within a documented bound and return the manager to a state that accepts a later normal request.

Local fault fixtures are configured through Yamcs command `CONFIGURE_SIMULATION`, are available only in the local profile, apply once to the next applicable operation, and then revert to `NORMAL`: `NORMAL`, `FAIL`, `NO_RESPONSE`, `DELAYED_RESPONSE`, `DUPLICATE_RESPONSE`, `HANG_CAPTURE`, and `DRIVER_UNAVAILABLE`. The `DRIVER_UNAVAILABLE` fixture returns the public `DRIVER_UNAVAILABLE` terminal status. Configure `DELAYED_RESPONSE` to arrive after the operation deadline; prove the request has one `TIMED_OUT` terminal result and its late callback is ignored. Exercise `BUSY` through overlapping valid operations, including reuse of the active external request ID, and exercise `INVALID` with a zero synthetic request ID or explicit legacy collection ID, empty literal, or invalid duration. The fixtures model software boundary behavior, not Aris's private protocol or the hardware profile. Do not invent a real payload acceptance response if Aris's interface provides none; expose only what is observed in the production adapter.

Aris's packaging and API have not been confirmed. Once supplied, define the exact byte/string boundary, termination, bounded response, and error behavior in the public contract. Keep private implementation details out of mission logic. Use request identifiers and synthetic strings in local evidence; decide logging policy before real command arguments enter Yamcs history.

### Product path decision

The installed `fprime-yamcs` service reconstructs stock F′ FilePackets (CCSDS APID 3) into a Yamcs bucket and checks the end-packet checksum. The October 7 compatibility probe commanded stock `FileHandling.fileDownlink.SendFile`, retrieved the object through Yamcs, and compared received bytes with the source oracle: **PASS, 26 bytes, product ID 1**, with matching SHA-256 recorded in the runbook. This remains a manual stock-file diagnostic and does not satisfy the mission's required SatNOGS/SDR science-return path. The later B software acceptance proves a separate local channel-1 reconstruction and Yamcs receipt; it still does not establish the SatNOGS/SDR receiver contract or physical route.

The mission science route remains custom channel 1. The accepted host test adapter reconstructs independently received PTY bytes before publishing into Yamcs [object storage](https://docs.yamcs.org/yamcs-server-manual/data-management/buckets/); copying/uploading the source file is insufficient. Connecting that receiver to SatNOGS/SDR still requires the firmware packet/throughput contract and mission-ops/FSW agreement. CFDP or stock FileDownlink remain separate choices for any future route.

Yamcs [command verifiers](https://docs.yamcs.org/yamcs-server-manual/mdb/loaders/sheet/command-verification/) can express execution/completion stages. ## Flight-scale gaps deliberately outside the local MVP

The stated December FSR minimum is a selected nominal Base/collection/processing sequence, time-based execution, EPS-controlled payload power, and science return. The SDD's fuller seven-mode model and guards, safe boot/exit, commissioning/deployment inhibits, contact-loss policy, persistent schedules/catalog, storage reclamation, time/context validity, authentication/replay protection, memory/state integrity, and target measurements remain separate follow-up scope. Minimal SOH is desirable; SAFE is the highest-priority additional mode if there is capacity. ADCS/geo-based commanding/HIL D2S2 remain lower priority and hardware-dependent. None of these are satisfied by a successful local Yamcs ping.

Keep iOBC/FreeRTOS OSAL, scheduling, 1 MB NOR code-budget feasibility, SDLS/framework migration and exact flight buses as separate target gates. The payload, radio and EPS contracts cannot be inferred from Artemis wiring. Preserve the working proxy demonstration as comparison evidence while those decisions close.
